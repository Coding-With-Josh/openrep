# openrep, technical notes

this is a reference document for anyone picking this codebase back up, including us. it explains how the pieces fit together and how the system is meant to work end to end. the code is currently stubbed, so where a section describes behavior that is not yet implemented that is called out explicitly. the "as designed" descriptions below are the contract the implementations should match.

## architecture overview

openrep is a pnpm monorepo with three packages.

- `packages/sdk`, published as `@openrep/sdk`. the core library. plain typescript, no framework, no react, no next. it owns the identity model, the attestation model, score calculation, ingestion, and resolution. everything that matters lives here so it can be reused by every surface without duplicating logic.
- `packages/cli`, published as `@openrep/cli`. a commander based command line tool. it depends on `@openrep/sdk` and exists for developers who want to script openrep into pipelines, ci checks, or their own agent tooling without a browser. every command is a thin wrapper around an sdk function.
- `apps/web`, named `web` in the workspace. a next.js app router application using typescript and tailwind. it also depends on `@openrep/sdk`. it is the human facing product: create agents, chat with them, watch reputation build live.

the dependency graph is a simple chain. the sdk depends on nothing local. the cli depends on the sdk. the web app depends on the sdk. nothing depends on the web app or the cli. that keeps the sdk the single source of truth for all reputation logic.

it is structured as a monorepo for two reasons. first, the sdk, cli, and web app all need to share the exact same types and logic, and a local workspace link means they compile against the same source rather than against a published copy that can drift. second, the sdk is small and pure, so keeping it as its own package means it can be published on its own later without dragging in react or next.

workspace links are handled by pnpm through the workspace protocol. both the cli and web app declare `"@openrep/sdk": "workspace:*"`, and pnpm creates a symlink from each of their `node_modules` to `packages/sdk`. the root `pnpm-workspace.yaml` lists `packages/*` and `apps/*` as the package globs. root scripts: `pnpm dev` runs the web app, `pnpm build` builds every workspace with `pnpm -r build`.

## identity model

an agent's identity is two keypairs plus a human readable name. when a new agent is created, `createAgent(options)` does four things: validate the caller's options, generate two keypairs, generate a human readable name, and produce a signed manifest that is persisted through the injected `StorageAdapter`. the caller passes only the interface, never a concrete database, so the function cannot depend on a specific backend.

each keypair is ed25519. ed25519 is chosen because it is the de facto standard for this kind of thing, it is fast, the signatures are compact (64 bytes), and it is available across languages, which matters for a platform that is meant to be read by many ecosystems. the private keys stay with the agent and are never transmitted. the public keys are what get published in the manifest and used by anyone verifying the agent's attestations.

the two keys are deliberately separated by role. the identity keypair (`publicKey`/`privateKey`) signs routine attestations; the owner keypair (`ownerPublicKey`/`ownerPrivateKey`) authorizes revocation alone. the separation exists because the identity key is the one used constantly and therefore the most exposed, and it must never double as the kill switch: whoever holds the owner private key can permanently revoke the agent, so losing it is far more consequential than losing the daily-use identity key, and is expected to be stored with correspondingly more care. the two keys are generated independently and are compared at creation so they can never coincide.

the implementation uses `@noble/ed25519` v3, the async api only (`keygenAsync`, `signAsync`, `verifyAsync`), which is webcrypto backed and avoids the sync api's requirement to wire a global sha512 signal by hand. verification always uses the strict rfc8032 branch (`{ zip215: false }`), not the more permissive zip215 default, because for a reputation ledger the strict branch is the correct default. all keys and signatures are lowercase hex strings, a decision that was confirmed across the whole sdk and reflected in the manifest fields below.

the human readable name is generated from three exported word lists (`ADJECTIVES`, `NOUNS`, `COLORS`, 36 words each) into the `adjective-noun-color.agent` shape, chosen from the same webcrypto csprng used for keys. the name is not security, it is ergonomics. it gives people and logs something memorable to refer to instead of a raw hex public key. the cryptographic identity is the keypair.

name uniqueness is deliberate. safety comes from a unique constraint on the name column in the storage backend, never from a client side check: two concurrent `createAgent` calls can both see a name as free, and the constraint is what makes exactly one of them win. the sdk's optimistic `getAgentByName` read is an optimization only, and adapters surface a constraint violation by throwing an error whose `code` is exactly `"DUPLICATE_NAME"`, which the sdk maps to a retry with a fresh name, bounded at 10 attempts and then reported as `NAME_GENERATION_EXHAUSTED`. a caller supplied name that collides returns `DUPLICATE_NAME` and is never silently renamed.

one explicit decision drives the whole type system: an agent is canonically identified by its public key everywhere, in attestations, storage keys, and lookups. the human readable name is a mutable, resolvable alias on top of the public key, never the canonical id, since names can be renamed later. this is documented at the top of `packages/sdk/src/types/identity.ts` so every later module follows the same rule.

the signed manifest is the portable identity card. field by field:

- `name: string`. the human readable name described above, for example `beautiful-pig-black.agent`. this is the mutable alias, not the identity.
- `publicKey: string`. the agent's ed25519 public key, lowercase hex. this is the canonical id and what signatures are verified against.
- `ownerPublicKey: string`. the agent's owner ed25519 public key, lowercase hex. this is the separate authorization key described above: the identity key signs attestations, the owner key authorizes revocation, and the two never coincide.
- `memoryPointer: string | null`. an optional uri (`ipfs://`, `https://`) pointing at the agent's memory or profile, or null when unset.
- `permissions: AgentPermission[]`. a closed string-literal union of granted scopes, currently `"attest:self" | "ingest:external"`, never a free-form array.
- `createdAt: string`. an iso 8601 utc timestamp of when the agent was created. this format is used consistently everywhere in the codebase.
- `manifestVersion: number`. a schema version so the manifest can evolve without breaking old manifests. version 2 added `ownerPublicKey`; manifests still at version 1 (created before the key split) are verified against their exact original six signed fields, so legacy signatures stay valid.
- `signature: string`. the ed25519 signature over the manifest fields above it, produced with the identity private key, lowercase hex.

the signature proves that whoever holds the private key generated and stands behind this manifest. the signed bytes come from `canonicalize`, the deterministic serializer in `src/canonical.ts`: recursive, object keys sorted, no whitespace, so the same logical manifest always produces the same bytes regardless of key order or formatting, which is what keeps verification portable across implementations. verification is the inverse: take the public key, re-canonicalize the signed fields (excluding the signature itself), and check the ed25519 signature with the strict rfc8032 branch. because the schema is versioned and `manifestVersion` is itself signed, `verifyManifest` can branch on the version without exposing a tampering path: a v1 manifest re-canonicalizes exactly the original six fields, a v2 manifest the seven including `ownerPublicKey`, and relabeling a version breaks the signature. `verifyManifest` is async (matching the noble v3 async api) and shape-validates every field first, returning `{ valid: false, reason }` with a specific reason string for malformed or tampered manifests instead of throwing. it also consults the stored agent record: a manifest whose agent has been revoked fails with reason `key revoked`, and a manifest whose agent has no record at all fails closed with `agent not found`. if it verifies, the manifest came from the keypair that owns that public key. this is what lets a verifier trust an agent without trusting the openrep server, because verification needs only the public key and the payload, both of which travel with the agent.

`AgentIdentity` extends the manifest with the private key. it exists only inside the sdk right after generation and is never the return type of anything exposed to an api route or the browser, by construction of the types in `types/api.ts`.

a key rotation record (old public key, new public key, signer, timestamp) is defined now even though rotation is not implemented, so the storage schema does not need a breaking change later.

## key custody policy

private keys are generated server-side and never transmitted to or stored in the browser, at any point, including the moment of agent creation. the frontend receives only the public manifest. this is not because of financial risk, attestations are not funds, it is because the agent's identity should be attributable and controlled by the server-side execution context that acts on its behalf, not exposed as a client-side secret with no real protection.

the policy is typed in `packages/sdk/src/types/security.ts` as `KeyCustodyPolicy` plus comments, not just prose. the rules:

- if an agent's private key does not need to persist beyond a single request, it exists only in process memory for the duration of that request and is never written anywhere.
- if it needs to persist across a session (an agent signing multiple attestations across a multi-turn chat), it is encrypted into an `EncryptedKeyRecord` with the server master key before being placed in the `SessionKeyStore`, and decrypted only in memory, only at the moment of signing.
- raw, unencrypted private keys are never written to disk, a database, logs, or any persistent store, under any circumstance.

for this pass, `createAgent` returns the private key only in memory to the server side caller and persists nothing but the public manifest (the `AgentRecord` is constructed field by field, never by spreading the identity, so the record type structurally cannot carry key material). the aes-256-gcm envelope encryption and the `SessionKeyStore` are typed and designed but not implemented yet. that is an explicit decision, not an oversight: single request flows do not need persistence, but before `createAgent` is wired into the multi-turn chat ui, session key persistence must be implemented or the agent cannot sign across turns.

the encryption is aes-256-gcm, stated explicitly on `EncryptedKeyRecord.algorithm`. the server's own symmetric key is loaded from the environment by `getMasterKey()`, which throws a typed `OpenRepError` with code `MISSING_MASTER_KEY` when it is missing. it never proceeds with an empty or default key, and the key value is never logged, never committed, and never included in any error message or stack trace. `EnvConfig` requires `masterEncryptionKey` and `databasePath` at load time through `loadEnvConfig()`, which fails loudly with a typed result rather than proceeding with undefined.

the `SessionKeyStore` interface is storage agnostic: get, set, delete, and clearExpired. session-scoped keys must have a real expiry, they do not live forever. the concrete implementation for this pass can be an in-memory store with expiry, but calling code depends only on the interface so it can be swapped for a real backing store without changes.

### abuse prevention

what stops an agent or user from spamming `attest()` to inflate a score, stated explicitly: for this hackathon, basic rate limiting only. the types exist now, `RateLimitConfig` and `RateLimitState` in `security.ts`, and the `RATE_LIMITED` error code is defined, but actual enforcement is wired up in a later pass. producing production-grade protection would require stronger anti-sybil measures, per-source trust caps, and identity verification of attestors. that is an explicit, written decision, not silence, and it is listed in known limitations below.

## attestation model

an attestation is proof that an agent completed a specific piece of work. it is not a claim, it is a signed record of what actually happened. openrep's own attestations all use the same shape.

the `Attestation` type, field by field:

- `id: string`. a unique id for this attestation, distinct from the agent id.
- `agentId: string`. the canonical id (the public key) of the agent this attestation is about, per the identity decision.
- `task: string`. a description of what the agent was asked to do. this is the prompt or task statement, kept as evidence of the work.
- `output: string`. what the agent actually produced. for a chat run this is the model's response text. for a tool run it can be the tool result, serialized.
- `toolsUsed: ToolCall[]`. an array of `{ tool, input, output? }` records of the tools invoked during the run, empty when none.
- `source: string`. who is vouching for this attestation. values for openrep's own runs are `native` or a named surface like `chat` or `cli`. for ingested external work this carries the registered external source name, for example `github` or `stripe`. the source is what lets scores be broken down.
- `contentHash: string`. a hash of the deterministic serialization of task, output, and toolsUsed. this is what actually gets signed.
- `signature: string`. the ed25519 signature over contentHash, produced with the agent's private key.
- `signedBy: string`. the public key that produced the signature.
- `timestamp: string`. an iso 8601 utc timestamp of when the work happened.
- `schemaVersion: number`. a schema version so the shape can evolve without breaking old rows.

producing an attestation during a real run is the job of `wrapAgent`. `wrapAgent(params)` takes explicit dependencies and runs a real multi-turn model conversation against claude or gpt, then signs an attestation for what happened. `params` carries `agentId` (the agent's public key), `signingKey` (the identity key used by `attest`), `storage` (the `StorageAdapter`), `config` (an `AgentConfig` with `provider`, `model`, and `tools`), `tools` (a map of executable implementations keyed by exact tool name), `apiKey` (the provider key, never stored or logged), `task` (the incoming prompt), and optional `options` (`source`, `idempotencyKey`). wrapAgent never reads environment variables or calls `loadEnvConfig` itself; everything it needs is passed in. it selects a provider adapter by `config.provider`, runs the loop below, and on success calls `attest` to sign and persist the run, returning `{ output, toolsUsed, turns, attestation }`.

the run loop is bounded and fail closed. the model conversation continues across turns until the model returns a final text response: the loop sends the accumulated messages, and each provider response is either a text answer (the run converges) or a tool request. a tool request is only honored if the tool name appears in the offered `config.tools` and has a matching implementation in `tools`; anything else is a protocol violation (`UNREGISTERED_TOOL`) and is never executed. the model-supplied arguments are validated against the tool's `inputSchema` before the real implementation runs (`TOOL_ARGUMENT_INVALID` otherwise), so model-generated input never reaches an implementation unchecked. tool results, including thrown errors captured as structured failure output, are fed back to the model so it can recover. the loop enforces `MAX_TURNS = 10` turns (`TURN_LIMIT_EXCEEDED` on non-convergence) and a whole-run wall-clock budget of `MAX_RUN_MS = 120s` via a single `AbortController` that also aborts the in-flight provider request (`RUN_TIMED_OUT`). a provider api failure that prevents a final answer is `PROVIDER_API_FAILURE`. in every one of those terminal states no attestation is produced; `attest` is only ever called once the loop converges on final text, so a run that timed out, hit the turn cap, or failed at the provider leaves no record behind. the provider-specific request and response parsing lives only inside the two adapters (`AnthropicClient`, `OpenAiClient` in `src/providers/`), which expose a common `ProviderClient` interface so the loop never sees provider wire shapes.

`attest(input, signingKey, storage)` is the signing primitive, where `input` includes `agentId`, `task`, `output`, `toolsUsed?`, `source`, and an optional `idempotencyKey`, and `storage` is the `StorageAdapter` the attestation is persisted through. input is validated at the boundary before any crypto or storage work: `agentId` and `signingKey` must be 32-byte lowercase hex, the payload has documented size limits (task up to 4000 characters, output up to 8000, toolsUsed up to 50 entries, tool names up to 100 characters, each tool entry up to 4000 canonical characters), and a well formed key that does not derive to the claimed agent is rejected with `KEY_MISMATCH`. `source` must be exactly `native`; anything else is rejected with `INVALID_SOURCE`, because external sources belong to `ingest` and this is the line that keeps the native ledger distinguishable from imported data. it computes the contentHash as the sha-256 of the canonical serialization of exactly `{ task, output, toolsUsed }`, signs the content hash bytes, not the raw fields, so any change to task, output, or toolsUsed invalidates the signature, records a server side timestamp, and assigns a random uuid as the attestation id (not a content derived id, so two legitimately identical runs can both exist). only then does it persist through `saveAttestation`, with no agent existence pre-check: the foreign key decides, and a violation surfaces as `AGENT_NOT_FOUND`. the optional `idempotencyKey` lets a retried submission from a flaky pipeline collapse into the same attestation instead of being double counted toward the score. idempotency is enforced by a composite unique index on `(agent_id, idempotency_key)`, not by the client: `attest` does an optimistic read first, but if a concurrent call wins the insert between the read and the write, the storage layer surfaces `DUPLICATE_IDEMPOTENCY_KEY` and `attest` resolves it by fetching and returning the existing record. signing ties the attestation to the identity: anyone with the public key can verify the attestation was produced by the agent's keypair and that the payload was not tampered with.

`verifyAttestation(attestation)` is the matching verifier and never throws. it shape-checks each cryptographic field with a specific reason, recomputes the content hash from `{ task, output, toolsUsed }` and compares it (`content hash mismatch` on divergence), then verifies the signature over the content hash bytes under `zip215: false` (`signature verification failed` on a bad signature). `canonicalize`, which all of this rests on, rejects circular references and nesting beyond a depth of 6, so crafted tool input cannot hang or crash the hashing path.

for the claude/gpt case specifically, the flow is: the user sends a message, `wrapAgent` sends it to the model api through the provider adapter, the model returns a response and possibly tool calls, the loop executes the offered tools (validated, captured, fed back) until the model produces final text, and `wrapAgent` turns the request text plus the response text and the recorded tool calls into the attestation payload. the model's response is the `output`. the tool calls are recorded in `toolsUsed` as part of the evidence chain and become part of the hash, so a later change to what the model actually did would invalidate the signature.

## ingestion model

ingestion is how openrep merges reputation that was created somewhere else. not every platform writes openrep format attestations, so `ingest` exists to normalize external records into the same schema.

external platforms hand over raw records shaped like `ExternalAttestation`: a loose `Record<string, unknown>` plus a required `sourceName`. this is intentionally loose because it is raw input before normalization, and it is the one legitimate sample/mock type in the project, clearly commented as such in `types/attestation.ts`, since there are no live external platforms to pull from during a hackathon. `ingest` normalizes the raw record into a native `Attestation` through a registered `SourceAdapter` for that source name, verifies it where the adapter provides a `validate`, and stores it under the local agent that matches the external name.

each external source is registered with a `RegisteredSource` that carries a `trustWeight`. the trust weight is a real multiplier applied when computing the composite score, not all sources count equally. a source that is more vetted counts more than a brand new one. this is what makes ingestion pluggable instead of hardcoded per platform: adding a platform means registering an adapter, not editing ingest logic.

the `source` field is what carries platform awareness through the unified schema. every attestation, native or ingested, records where it came from. that single field is what makes the score breakdown by source possible, and it is the mechanism that keeps openrep platform agnostic: it does not care which chain or marketplace produced an attestation, it only records the origin and folds it into the same per-agent ledger.

the composite score is computed by `getScore(agentId, storage, options?)`, which returns `Result<AgentScore>`. `AgentScore` has an `agentId`, a single `composite` number, a `breakdown` array of `ScoreBreakdown` entries, and a `computedAt` timestamp. each breakdown entry has a `source`, a `value` (the per-source score in the same scale as composite), a `count` (the number of attestations that source has contributed), and a `lastUpdated` timestamp (the newest attestation the source has on record). the formula is exact and implemented once:

```
composite = sum over sources of ( value_source * trustWeight_source )
value_source = count_source
```

every number in the result traces to real rows read through the storage adapter, never to a hardcoded value. `getScore` pages the full attestation history until exhausted (rows are immutable and the cursor is over `row_id`, so a page can never shift or duplicate); a history larger than the exported `SCORE_MAX_ATTESTATIONS` (50,000) fails closed with `SCORE_COMPUTATION_LIMIT_EXCEEDED` rather than returning a truncated score. an existing agent with zero attestations scores a valid `0` with an empty breakdown; an unknown agent is `AGENT_NOT_FOUND`. per-source weights: `native` is pinned to trust weight `1.0` and never needs (and cannot be overridden by) a row in `registered_sources`, registered external sources use their stored `trustWeight` (non-finite or negative values are clamped to `0`), and an unregistered non-native source contributes `0` to the composite while staying visible in the breakdown so its history is not hidden. the breakdown is returned sorted by source name for deterministic output. decay defined in `ScoringConfig` is not enabled in this pass (the type exists so enabling it later is not a breaking change), and nothing is cached: every call recomputes from the ledger, which stays append-only. openrep stays platform agnostic because the score is always presented as a composite plus a per-source breakdown, never as a single number locked to one chain's semantics.

`resolve(name, storage)` ties the two models together: it looks up an agent by its human readable name alias and returns a `ResolveResponse` containing both the manifest and the live `AgentScore`. the resolved manifest is `ResolvedManifest` (`AgentRecord` minus the storage-internal `rowId`), so it carries `ownerPublicKey` and `revokedAt` without leaking an internal index into a network type. `resolve` is a thin composition of `getAgentByName` + `getScore` with no scoring logic of its own, so there is exactly one implementation of the math. a caller that only knows a name gets everything needed to verify the identity and read the reputation.

## storage

this is a hackathon build, and the storage is deliberately honest about being local. the concrete backend is sqlite through the node built-in `node:sqlite` (`DatabaseSync`), which ships in node itself so the sdk still has no native dependency and no extra install step. using it requires node `>= 22.13`, which the `engines` field of `packages/sdk/package.json` enforces. there is no server, no network service, and no distributed system. all persistence lives inside the sdk package and is exercised directly by the cli and web app.

the storage contract is `StorageAdapter` in `types/storage.ts`, and calling code depends only on that interface, never on the sqlite backend directly. application code opens a connection through `getSqliteStorage(databasePath)`, which memoizes one open connection per path per process, and tests use `createSqliteStorage(":memory:")` for a fresh isolated database per test. the database path is never hardcoded in the adapter: it comes from the caller, and in the cli and web app it will come from `EnvConfig.databasePath` through `loadEnvConfig` once that is implemented.

the schema is three tables, created by an idempotent `CREATE TABLE IF NOT EXISTS` bootstrap that runs at construction. this is a deliberate migration choice: the project is pre-release with no deployed databases to migrate, so a numbered migration runner (sql files plus a `schema_migrations` table) would be processional. additive schema changes are appended with `IF NOT EXISTS`. the moment real user data exists anywhere, a numbered migration strategy becomes warranted.

- `agents`. columns: `row_id` (internal index), `name` (unique, the mutable alias), `public_key` (canonical id, also unique), `owner_public_key` (nullable), `memory_pointer`, `permissions` (json), `created_at`, `manifest_version`, `signature`, and `revoked_at` (nullable). the agents table never contains either private key, ever. `owner_public_key` is nullable because rows created before the key split genuinely have no owner key on record, and the sdk fails closed on those (they can never be revoked, surfaced as `OWNER_KEY_MISSING`) rather than inventing an authorization path for old data. `revoked_at` is null until a valid, authorized revocation request stamps it. the unique constraint on `name` is the enforceable source of truth behind createAgent's collision handling (the sdk's optimistic read is an optimization only), the unique constraint on `public_key` is a second line of defense, and `saveAgent` additionally asserts at runtime that the record carries no private key so key material can never reach the disk even if the type system is bypassed. the private keys live only in memory or in an encrypted envelope in the session key store per the key custody policy.
- `attestations`. columns: `row_id`, `id` (unique), `agent_id` (foreign key to `agents.public_key`, enforced per connection), `idempotency_key` (nullable), `task`, `output`, `tools_used` (json), `source`, `content_hash`, `signature`, `signed_by`, `timestamp`, and `schema_version`. the foreign key is what makes saving an attestation for a nonexistent agent fail at the schema level, surfaced as an error with code `AGENT_NOT_FOUND`. the unique index on `(agent_id, idempotency_key)` is the authoritative guard behind `attest`'s idempotency contract: the same pair can only ever insert once, while null keys remain unbounded because sqlite treats nulls as distinct in unique indexes.
- `registered_sources`. columns: `source_name` (primary key), `registered_at`, and `trust_weight`. this is where the trust weights used by scoring live, one row per approved external source.

the unique and primary key constraints create their own indexes, so the only additional indexes are on `attestations.agent_id` (the attestation paging lookup) and the composite `(agent_id, idempotency_key)` (the idempotency guard). databases created before a new column landed are upgraded in place when the adapter opens them: because the original `CREATE TABLE IF NOT EXISTS` cannot alter an existing file and sqlite has no `ADD COLUMN IF NOT EXISTS`, the opener checks `PRAGMA table_info(<table>)` and runs a guarded `ALTER TABLE ADD COLUMN` per missing column, and the whole sequence is idempotent across repeated opens. this covers the idempotency column on `attestations` and both revocation columns on `agents` (`owner_public_key` and `revoked_at`). a pre-existing database that was created before the key split keeps its legacy agent rows with a null `owner_public_key`, and those rows fail closed on revocation exactly as described above.

both `AgentRecord` and `AttestationRecord` extend their portable counterparts with an internal `rowId`, so the persisted rows carry an index without polluting the signed payload. on `AgentRecord` the `rowId` is optional: it is assigned by storage at insert time, so the sdk never needs it when building a record to save.

the storage error contract is part of the interface. `saveAgent` throws an error whose `code` property is exactly `DUPLICATE_NAME` on a name collision and `DUPLICATE_PUBLIC_KEY` on a public key collision, `saveAttestation` throws `AGENT_NOT_FOUND` when the referenced agent does not exist and `DUPLICATE_IDEMPOTENCY_KEY` when the `(agent_id, idempotency_key)` index fires, `revokeAgent` throws `AGENT_NOT_FOUND` when zero rows match (a disappearing agent), and `saveRegisteredSource` throws `DUPLICATE_SOURCE_NAME` on a duplicate source name. everything else propagates as the raw node:sqlite error, so a disk failure is never miscategorized as a name conflict. the classification matches the exact node:sqlite error shape (`code` `ERR_SQLITE_ERROR`, unique violations carrying `UNIQUE constraint failed: <table>.<column>` in the message, foreign key violations carrying `FOREIGN KEY constraint failed`), verified against node 24.10.0 before the mapping was written.

`agents.name` is unique because `resolve` looks agents up by name. the `attestations.agent_id` foreign key is how all reputation funnels back to one identity. scores themselves are not stored, they are computed on demand from the attestation table by `getScore`, which keeps storage append only and avoids stale scores. list-returning storage methods take `{ cursor?, limit? }` and return `{ items, nextCursor }`, the standard paginated shape defined once in `storage.ts` and reused by the activity feed. `getAttestations` pages newest first with a cursor over the immutable `row_id` (`row_id < cursor` for the next page), so rows inserted between page loads can never shift or duplicate an already returned page, unlike offset pagination.

this design is fine for a demo, and it is a real weakness for production. there is no durability story across machines, no access control, and no multi tenancy. anyone who could read the file could read or forge the data, which matters because without a trusted service the only real protection is the signatures themselves. the storage is treated as honest but single user.

## activity feed

the `ActivityEvent` type in `types/activity.ts` includes an `agent_created` variant for a future live feed. in this pass `createAgent` intentionally does not emit activity events: the feed is not built yet, and emitting events now would be dead code. this is a written deferral, not an oversight. when the feed is built, wiring `agent_created` into the create path is part of that work, not a new decision.

## the web app

the web app is a next.js app router application that imports `@openrep/sdk`. because the sdk is plain typescript with no server dependency at runtime, it can run on the server, and that is where the reputation state should live.

the intended setup keeps the sdk on the server side, behind next.js api routes or server actions. the flow is: the server imports the sdk, and the client browser components never hold the private keys. a user creates an agent through a server call that runs `createAgent` and returns the public manifest and a handle. the private key stays server side, tied to the session or the agent record. letting private keys reach the browser would defeat the whole signing model, so the boundary between client and server is also a trust boundary.

the chat flow, end to end: the user selects an agent in the sidebar, types a message in the chat panel, and hits send. the message goes to a server action or api route. the server loads that agent's keypair and the provider api key from its own configuration, runs the model call (claude or gpt) with `wrapAgent` by passing `agentId`, `signingKey`, `storage`, the agent's `AgentConfig`, the tool implementations, `apiKey`, and the message as the `task`. wrapAgent runs the bounded loop, captures the task, the tool calls, and the output, and signs and persists an attestation through the storage adapter. the server returns the model's reply to the browser. the browser renders the reply. the score component on screen calls `getScore` for that agent again, and because a new attestation was just stored, the composite and the breakdown tick up. nobody in that loop manually bumps a number, the score update is a pure consequence of storing a new attestation. the api key travels from server configuration to the provider adapter and nowhere else; it never enters the captured attestation data, the logs, or the browser.

multiple agents per user are modeled as multiple rows in the `agents` table. each has its own id, name, keypair, and attestation history, and therefore its own independently computed score. the app shows one score per agent, and the comparison view renders all of an agent's breakdowns side by side. the current `page.tsx` is an empty fragment, so none of this is built yet; this section is the design it should converge on.

## the cli

the cli maps one to one onto sdk functions. `openrep create` calls `createAgent`. `openrep attest` calls `attest` with the flags as arguments. `openrep ingest` reads the file and calls `ingest`. `openrep score` calls `getScore` through `resolve`. `openrep resolve` calls `resolve`. each command carries the relevant flags to keep it scriptable without a browser. parsed argument shapes live in `packages/cli/src/types.ts`, kept separate from sdk input types so file parsing failures are distinguishable from sdk validation failures.

`openrep verify` is the outlier and the most important one for trust out of a pipeline. it does not call the score functions. instead it takes an agent, pulls the full attestation history, re-hashes each attestation's payload, and checks each signature against the agent's public key, all locally and with no need to trust the openrep server. the public key comes from the signed manifest, and the manifest itself is verified first. if every manifest signature and every attestation signature checks out, the attestation history is intact and the agent is who it claims to be. this is what makes verify useful for ci or third party audits: it needs nothing from openrep's infrastructure beyond the data on disk, and it produces an independent, cryptographic answer.

## cli key custody policy

the cli needs its own custody policy because it has no separate server. in the web app, the browser is untrusted and the server is the trusted custodian holding keys on the user's behalf. in the cli there is no such split: the process runs directly on the user's own machine under their own os account, and each command is a separate process that does not share memory with the previous one. the user is both the operator and the owner of the agent, so the question is not "keep the key away from the user", it is "where does the key persist on their machine between separate cli invocations". the cli supports two usage modes and the policy differs for each.

### interactive local use

a developer running commands on their own machine. the private key should be stored in the os-level secure keychain: macos keychain, windows credential manager, or linux secret service, accessed through the os's native credential store interface. the implementation is free to use whatever tooling best fits, the policy intentionally names no library so it does not go stale if the library choice changes. if no os keychain is available (for example some minimal linux environments), the cli falls back to an encrypted file on disk, `~/.openrep/credentials.enc`, encrypted with aes-256-gcm under a key derived from a user-supplied passphrase (pbkdf2 or scrypt), protected by strict file permissions (owner read/write only) as a second layer of defense. the derivation secret is the passphrase, never a key stored next to the file, so the fallback keeps a real secret at its root. under every fallback path the private key is never written to disk in plaintext. this mirrors the pattern used by git credential managers and ssh agent for the same reason: a real secret that needs to persist across separate cli invocations on a single-user machine.

in interactive mode, `openrep create` automatically stores the generated private key into the keychain (or the fallback store), because custody between separate invocations is the whole point of the mode. the stored entry is keyed by the agent's canonical id, the public key, never by the mutable name, since names can be renamed.

### headless and ci use

a pipeline calling the cli non-interactively, for example github actions. here openrep does not attempt to take custody of the key at all. the expected pattern is the one used for aws credentials and ssh deploy keys: the pipeline's own secret manager holds the key and injects it into the cli's environment per run, via an environment variable or a mounted file path. the cli reads the key for that single invocation only and never persists it, not to a keychain, not to a file, not anywhere. openrep taking custody in this context would be worse practice than not doing so, because it would duplicate a responsibility that already belongs to the pipeline's existing secret management.

### mode selection

the cli must support both modes, it does not choose one. a single flag or environment variable convention determines which mode is active: if a key is supplied via environment variable or mounted file at invocation time, the cli uses it directly for that call and does not persist it; otherwise it falls back to the os keychain flow for interactive use. the exact flag and environment variable names and the payload form are finalized in the cli implementation pass; the decisions that both modes must exist and that an injected key wins over persistence are settled now.

## known limitations

these are the honest simplifications, so nobody mistakes this for production grade infrastructure.

- storage is local and single user. sqlite or a json file on disk, no server, no durability across machines, no access control, no multi tenancy.
- external attestations are mocked as sample data for the demo. there are no live integrations pulling real attestations from other platforms or chains, so ingest is exercised against hand written sample input that looks like what a real platform would produce.
- there is no payment or staking layer. reputation here is purely attestation derived; there is no economic component, no token, and no way for reputation to carry monetary weight.
- the web app has no authentication. it is a single user demo. there is no notion of accounts or ownership beyond the local agent rows.
- abuse prevention is rate limiting only, and the rate limiting types exist but enforcement is wired up in a later pass. production would need stronger anti-sybil measures, per-source trust caps, and attestor identity verification.
- there is full key revocation but no key rotation. revocation exists and is real: each agent has a separate owner key that alone can permanently kill the agent, and `revokeAgent` in the sdk enforces it. rotation, by contrast, is not implemented. `KeyRotationRecord` is typed so the schema does not need a breaking change later, but nothing rotates a key today, and `attest` signs with whatever identity key the caller holds. the two are distinct and the gap is specifically rotation: if the identity key leaks but the owner key does not, the agent can and should be revoked rather than rotated, and revoking is the available response today. true rotation (silently re-keying an existing agent) is a real, unaddressed gap for production, not a cosmetic one.
- revocation is authorized by owner key only. `revokeAgent` takes a request carrying a fresh ed25519 signature over `{ agentId, timestamp }`, verified against the agent's stored `ownerPublicKey`. holding the day to day identity key is not enough to revoke, which is the whole point of the two-keypair split. the timestamp must fall inside a symmetric five minute replay window (`REVOCATION_REQUEST_MAX_AGE_MS`), so a captured old request can never be replayed: outside the window it fails as `STALE_REVOCATION_REQUEST`. a wrong signer fails as `UNAUTHORIZED_REVOCATION`, a legacy row with no owner key fails closed as `OWNER_KEY_MISSING`, and revoking an already-revoked agent is an idempotent success that writes nothing twice. once an agent is revoked, `attest` refuses to sign for it (`AGENT_REVOKED`) and both `verifyManifest` and `verifyAttestation` report `key revoked`, so revocation wins over an otherwise valid signature.
- `attest` and `verifyAttestation` gate on revocation with a read of the stored record before doing any crypto, and that gate is a pre-check, not an atomic compare-and-swap with the attestation insert. `AGENT_REVOKED` is decided by the state as read at the start of `attest`; there is a theoretical window between that read and the save where a concurrent revoke could land. in-process, on the single memoized sync sqlite connection, the window effectively cannot occur, so this is not a live race in the current build. it stays an open item until the storage connection model is reworked for writes (the wal/concurrency task) and should be made atomic there. the ledger stays append-only: revoking an agent does not delete or rewrite its past attestations, it only stops future signing and makes the existing ones fail verification.
- revoked agents keep their historical score. this is a decided policy, not an accident: `getScore` counts a revoked agent's past attestations toward reputation unchanged (revocation is not a score reset, it stops future signing), and `resolve` surfaces revocation via `revokedAt` on the resolved manifest so a caller can see the revocation alongside the score. a separate policy for revoked history, if ever wanted, is a scoring-pass change, not a schema one.
- `attest` and `createAgent` emit no activity events in this pass. the activity feed is not built, and emitting events now would be dead code. `agent_created` already has a written deferral next to the feed design; the same deferral covers `attestation_created` style events until the feed exists.
- tool outputs are fed back into the model conversation during a wrapped run. this is a real, general, unmitigated prompt-injection surface: a tool that returns content from an untrusted source (a web search result, a fetched page) could influence the model's subsequent decisions in ways the attestation records but does not prevent. tool call requests from the model are gated (only offered tools execute, arguments are validated), so a model cannot be tricked into calling an arbitrary tool, and the attestation records exactly what did run. but the content of tool results is model input by design, so prompt injection via that content remains inherent to agentic tool use. it is documented here on purpose, not papered over.
- the sdk is partially implemented. `createAgent`, `verifyManifest`, `attest`, `verifyAttestation`, `revokeAgent`, `getScore`, `resolve`, the canonical serializer with its cycle and depth guards, `wrapAgent` with its provider adapters and bounded run loop, and the sqlite storage adapter (`createSqliteStorage`/`getSqliteStorage` in `src/storage/sqlite.ts`) are real and tested (see `packages/sdk/test/agent.test.ts`, `test/canonical.test.ts`, `test/attestation.test.ts`, `test/revocation.test.ts`, `test/storage.test.ts`, `test/wrapagent.test.ts`, `test/providers.test.ts`, `test/validate.test.ts`, `test/score.test.ts`, `test/resolve.test.ts`, `test/score.integration.test.ts`, and `test/integration.test.ts`), while `ingest` and `loadEnvConfig` still throw "not implemented yet". the cli and web app are still stubs. the descriptions above are the agreed design, the implementation is the work still to do.
- session key persistence (aes-256-gcm envelope encryption plus the `SessionKeyStore`) is not implemented. keys are memory-only today, which is fine for single request flows but must be scheduled before `createAgent` is wired into the multi-turn chat ui.
- scoring is recomputed from the full ledger on every `getScore`/`resolve` call with no cache. correct and fast at demo scale, but a history at or near `SCORE_MAX_ATTESTATIONS` (50,000) fails closed with `SCORE_COMPUTATION_LIMIT_EXCEEDED` instead of truncating; caching with a defined invalidation story is the natural follow-up when the cap matters.
- score weighting is a placeholder policy, not a researched formula. the implemented formula is exact (`composite = sum of count * trustWeight` per source) but the `trustWeight` numbers themselves are a starting point, not a standard, and the model is trivially gameable by a single source flooding attestations: nothing caps a source's contribution per run, and per-source caps are an anti-sybil measure deferred with the rest of the abuse prevention.
